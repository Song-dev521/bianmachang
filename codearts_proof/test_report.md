# 辩码场 · 码道流水线测试报告

> 测试人：组员 B ｜ 测试日期：2026-11-02 ｜ 测试环境：华为云码道（CodeArts）平台 · 智能体 IDE
> 测试对象：5 个独立 Skill（security-review / performance-review / architecture-review / standard-review / conflict-summary）+ 1 条多 Skill 并行流水线

---

## 一、测试目的

1. 验证 4 个评审 Skill 能否在各自维度内独立、专业地输出结构化评审结论；
2. 验证冲突汇总 Skill 能否识别不同评审视角之间的分歧，输出共识、冲突与多套可选方案；
3. 验证多 Skill 并行流水线端到端链路可运行、可复现。

## 二、测试环境与方法

- 所有测试均在码道平台内完成：单 Skill 在智能体对话窗口逐个输入代码样例测试；流水线在编排完成后进行整体联调。
- 测试代码样例存放于 `testcase/` 目录，运行输出记录存放于 `run_log/` 目录，关键界面截图同步归档。
- 每个测试环节均保留原始对话导出与截图，未做内容改写。

## 三、测试用例与结果

### 用例 1：`sql_inject_01.py` —— 含 SQL 注入 + 结构缺陷代码

代码特征：字符串拼接构造 SQL、`SELECT *`、连接仅正常路径关闭、函数名与返回值基数不一致、SQL 文本残缺。

**单 Skill 测试**（输出记录见 `run_log/skill_*_test.md`）：

| Skill | 结论 | 关键输出摘录 |
| ---- | ---- | ---- |
| security-review | 风险等级：高 | 识别 SQL 注入（Critical，CWE-89）、敏感字段过度暴露（CWE-213）、越权风险（CWE-862）等 9 项，并给出参数化查询修复实现 |
| performance-review | 性能等级：一般 | 指出连接按调用新建、语句缓存无法复用、`fetchall()` 全量物化等问题，并区分"单次可接受、规模化劣化" |
| architecture-review | 架构等级：有缺陷 | 指出零分层、依赖倒置缺失、资源生命周期归属悬浮等 8 项，给出端口/适配器重构建议 |
| standard-review | 规范等级：较多问题 | 指出 SQL 残缺不可执行、缺 docstring 与类型注解、魔法字符串、裸资源管理等，并按 P0–P3 分级 |

**流水线联调**（输出记录见 `run_log/pipeline_run_test.md`）：
一次输入上述代码，4 个评审 Skill 并行输出各自维度的完整结构化报告；汇总环节正确提取了"函数名承诺单实体 vs 实现返回集合"等 5 项共识、4 组权衡冲突（语义一致优先 vs 契约兼容优先等），并给出 4 条带取舍代价的可选方案。

### 用例 2：`case_normal.py` —— 干净无缺陷代码

验证目标：Skill 能识别"无风险"场景，不制造伪冲突。
结果：各评审维度给出整洁/低风险类结论，冲突汇总仅输出少量改进建议与取舍说明，未出现维度间对抗性冲突。运行截图见 `testcase/case_normal.py.png`。

### 用例 3：`case_simple_bug.py` —— 含明确 SQL 注入漏洞

验证目标：各维度漏洞检出能力。
结果：安全维度报出高危注入；性能维度指出全表扫描与无上限结果集；架构维度指出持久化细节未隔离；规范维度指出拼接写法与命名问题。冲突汇总在确认注入为多方共识的同时，识别出"修复注入引入参数化后与语句缓存复用、列裁剪等优化项的组合方式"等次级取舍。运行截图见 `testcase/case_simple_bug.py.png`。

### 用例 4：`case_conflict.py` —— 工程权衡冲突样例（核心）

代码特征：查询本身使用参数化绑定，**安全上没有明显问题**；但每次调用新建并关闭数据库连接，且在循环中调用 100 次。

验证目标：制造"安全 vs 性能"的真实评审冲突，验证冲突汇总 Skill 的核心能力。

结果（运行截图见 `testcase/case_conflict.py.png`）：安全维度不再报高危（对比用例 3），性能维度明确指出连接按次新建的开销随调用次数线性放大——**两个维度的关注点形成真实张力**。冲突汇总 Skill 输出了多套互斥方案并写明各自代价，例如：

- 方案 A（维持现状 + 安全加固）：保留每次新建/关闭连接，代价是循环内 100 次连接的性能损耗原样保留；
- 方案 B（性能优先，连接复用）：把连接提升到 main() 层建立一次、循环内复用，性能显著改善，代价是异常后连接状态污染、无法隔离，安全侧需额外增加连接有效性检查；
- 方案 C（架构优先）：抽出 DAO 层、连接由工厂注入，换取可测试与可替换，代价是引入分层与间接性；
- 方案 D（分阶段演进，推荐教学对照）：先解决安全与资源泄漏，再合并循环复用连接，展示真实项目的演进路径。

> 该用例是本项目教学价值的直接佐证：同一段代码，安全视角说"没问题"，性能视角说"有隐患"，两种说法都成立——不存在唯一标准答案，取舍取决于场景。

## 四、测试结论

1. 4 个评审 Skill 输出专业、结构完整、角色边界清晰，未出现维度互相越界；
2. 冲突汇总 Skill 能稳定区分共识、真实冲突与无关建议，并输出带取舍代价的多套方案；
3. 多 Skill 并行流水线端到端跑通，结果可复现；
4. 三类用例（无冲突 / 单一漏洞 / 工程权衡冲突）均得到符合预期的差异化输出，验证了"刻意保留冲突"的设计目标。
