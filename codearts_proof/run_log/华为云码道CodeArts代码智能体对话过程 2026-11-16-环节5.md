## 结论

问题出在 `max_tokens` 传入的值有误，接口本身没有出错。它表示整个 completion 的总输出预算，而不是可见正文的预算。`max_tokens=20` 全被思维链消耗掉，正文只剩 0 个 token，所以 `content=""`；`finish_reason="length"` 就是这次被截断的明确证据。

## 为什么 HTTP 200 + 空 content 而不报错

- 预算耗尽在 OpenAI 兼容协议里是**合法的完成状态**，由 `finish_reason="length"` 表达，不是协议错误。400/422 只用于参数非法（负数、超模型上限、格式错），不用于“正常生成但被截断”。
- 因此 SDK 不抛异常，`resp.choices[0].message` 正常存在，只是 `content` 为空、`reasoning_content` 有内容。
- 思维链模型生成顺序固定：**先 reasoning，后 content**。预算 20 时模型连推理都没走完，正文一个 token 都没轮到，于是得到“成功的空响应”。把预算调大后，推理先占用一部分，剩余部分才轮到正文，所以就能拿到内容。这与你观察到的现象完全一致。
- `temperature=0.3` 与它无关；800 字 system + 代码本身也吃输入 token，但输入不计入 `max_tokens`，不影响这个结论。

## 生产参数建议

**max_tokens：不要再以 20 为基线，按“正文预算 + 推理预算 + 余量”来给**

- 800 字中文评审正文 ≈ 1200–1600 token；代码评审类思维链通常 1500–3000 token。合计 4000+。
- 建议 **默认 4096**，对代码量较大的批次使用 **8192**。你现在 `providers.py:95` 的 2048 对“800 字 system + 整段代码”偏紧，仍可能偶发截断。
- 加一个启动期校验：`max_tokens < 1024` 直接拒绝初始化并告警，消除这类误配。
- 若该模型/网关支持 `max_completion_tokens`，优先用它（语义上明确覆盖推理+正文），避免 `max_tokens` 在部分推理模型上被忽略。

**超时：60s 不够，改 120s（`REVIEW_TIMEOUT`）**

- 思维链 + 4096 输出，单次常见 60–150 秒。`providers.py:93` 的 60s 会先把还在正常推理的请求掐断，表现成 `asyncio.TimeoutError` 而非空 content，容易误判。
- `asyncio.wait_for` 的超时要**略大于**模型侧超时（或显式给 `client` 配 `timeout=`），否则本地先断开，日志里看不到服务端真实报错。
- 四路评审若串行，注意总时长是单路的 4 倍，前端 SSE 需有进度心跳。

**重试：要分两类，不要一律重试**

- `finish_reason == "length"` → **不重试同参数**，必须**放大 `max_tokens` 后再试一次**（比如 ×2，封顶 8192），否则结果必然重复。
- 网络错误 / 429 / 5xx / 超时 → 指数退避重试，最多 2 次（1s、3s），只对这类幂等读取安全。
- `finish_reason == "stop"` 且 content 空 → 不重试，直接降级或报错，重试大概率还是空。

**一个必须改的点**：`providers.py:112-114` 现在空正文时回退 `reasoning_content` 当结果返回，这会把你判断依据抹掉，还可能让下游 `parse_level()` 把思维链文本当评审结论。正确做法是先判断 `finish_reason`，`length` 就抛可识别异常，再放大预算重试；不要静默拿思考过程顶正文。

### 1. API Key 从环境变量读取 —— 低危

**证据**
- `providers.py:81` `api_key = os.getenv("MAAS_API_KEY", "").strip()`，为空即抛 `RuntimeError`（:82-83），未硬编码、未写入配置文件、未拼进 model/base_url。
- `api_key` 是**局部变量**，仅通过构造参数传给 `AsyncOpenAI`（:89-92），未存为 `self.api_key`、未进任何日志语句。
- `.env.example:3` 值为空占位，无真实凭据。

**判定**：读取方式合规（环境变量是标准做法，优于配置文件和命令行参数）。Python 默认 traceback 不打印局部变量，所以常规崩溃**不会**把 key 打进堆栈。仅存的泄露通道是条件性的：`str(exc)` 若上游/网关把 key 回显在错误体里，再叠加维度 3 的透传就会外泄。

**补充（低危）**：`providers.py:155` 把 `{exc}` 对外输出，一旦 `AsyncOpenAI` 构造或 HTTP 层异常携带认证信息即失守 —— 归入维度 3 一并修。另需确认 `.env` 已在 `.gitignore`，且容器内环境变量对其他进程不可读（`/proc/<pid>/environ`）。

---

### 2. 模型白名单校验位置 —— 合规

**证据**：`providers.py:84-88` 在 `__init__` 读 `MAAS_MODEL` 后立即校验；`complete()`（:100）用的是 `self.model` 快照，不再读环境变量。

**判定**：**初始化时校验是正确的，不需要改成每次调用校验。** 理由三条：
1. fail-fast：非法模型在启动/构造阶段就失败，不浪费一次真实推理计费；
2. `self.model` 构造后不再变动、也无 setter，运行期改 `os.environ` 影响不到它，不存在“校验后模型被换掉”的绕过路径；
3. 每次调用重复校验属纯开销，且 `complete()` 拿不到外部传入的 model，无校验对象。

**唯一残余风险（低危）**：`ALLOWED_MODELS` 是模块级可变 `set`（:25），同进程内任何代码 `ALLOWED_MODELS.add(...)` 即可绕过。建议改为 `frozenset({...})` 冻结。仅当将来支持“请求级指定 model”（多模型路由）时，才需要把校验下移到 `complete()`，校验对象变为**用户传入值**。

### 3. 异常处理透传上游原始错误 —— 中危（本次最高）

**证据 1（直接命中）**：`providers.py:154-155`

```python
except Exception as exc:  # 依赖没装等
    return ReplayProvider(), f"MaaS 初始化失败，降级回放：{exc}"
```

该函数第二个返回值在 `build_provider()` 语义上是**对外提示信息**（:147/149/153/156 均为面向用户的文案），会经 SSE/接口展示。`{exc}` 是**原始异常字符串**，可携带模块路径、base_url、上游错误体。这正属于“把上游/内部原始错误直接透给前端”。

**证据 2（缺边界）**：`complete()`（:97-109）对 `chat.completions.create` **无任何 try/except**。401/403/429/5xx 抛出的 `openai.APIStatusError` 会原样冒泡；`resp.choices[0]`（:110）在空 choices 时抛 `IndexError`。若上层把它写成 `detail=str(e)` 或 SSE `error` 事件，上游响应体（含 request id、内部网关信息）直接出网；即使上层未捕获，debug 模式下 500 响应会带完整 traceback。

**判定**：文件层面**没有异常安全边界**，且存在一处明确的原始异常透传。中危。

**建议**：对外只输出错误**分类码**，原始异常仅进服务端日志且先脱敏（正则抹掉 `sk-`/`Bearer`/`api_key` 值）：

```python
except Exception as exc:
    log.warning("maas init failed: %s", _redact(str(exc)))
    return ReplayProvider(), "MaaS 初始化失败，已降级为回放模式"
```

`complete()` 外包一层 `try/except`，映射为稳定错误码（`AUTH_FAILED` / `RATE_LIMITED` / `UPSTREAM_ERROR` / `EMPTY_CONTENT`）再上抛，禁止把 `exc.args` 直接往外传。

### 4. 超时/重试参数 —— 中危

**证据与判定**

| 项 | 现状 | 判定 |
|---|---|---|
| 超时 | `REVIEW_TIMEOUT=60`（:93、`.env.example:15`） | **偏短**。思维链模型 4096 输出常见 60–150s，60s 会误杀正常请求，表现为超时而非空 content，干扰排障 |
| 重试 | **无**（全文件无 retry/backoff） | **不合理**。429/5xx/超时直接失败或静默降级回放，生产可用性差 |
| 预算 | `MAX_TOKENS=2048`（:95），且 `.env.example` 未列该变量 | 偏紧：800 字 system + 整段代码 + 思维链，易被 reasoning 吃空；运维也无从得知需调 |
| 参数校验 | `float()`/`int()` 直接转换，无下限 | 配成 `0`/负数时 `wait_for(timeout<=0)` 立即超时、`max_tokens<=0` 请求必败；配成非数字则在 init 抛 `ValueError`（被 :154 吞成降级提示） |

**额外隐患**：`asyncio.wait_for` 只掐外层 task，`AsyncOpenAI` 自带默认 timeout/retry 未显式设置，会出现“业务层 60s + SDK 层重试”双重计时，超时后连接可能不清洗。

**建议**：`REVIEW_TIMEOUT=120`；client 显式传 `timeout=` 与 `max_retries=0`（避免双重重试）；业务层只对 429/5xx/超时做指数退避重试**最多 2 次**（1s、3s）；`finish_reason=="length"` **不重试同参数**，放大 `max_tokens` 后再试一次；`MAX_TOKENS` 默认 4096 并在初始化时断言 `>=1024`、`REVIEW_TIMEOUT` 断言 `[30, 300]`。
