【性能问题清单】

位置：conn = sqlite3.connect('test.db')

问题：每次调用都新建数据库连接，函数返回前即销毁。

性能损耗原因：连接建立包含文件打开、页缓存初始化、编译选项解析等固定开销，且该开销与结果集大小无关；在高频调用或循环内调用时按调用次数线性放大。同时新连接不存在语句缓存复用，每次都要重新解析同一 SQL。

优化建议：由调用方或上层作用域复用连接；若确需自持，至少在同一批查询间共用一个连接对象。

位置：query = "SELECT * FROM users WHERE ..."

问题：使用 SELECT * 读取全部列。

性能损耗原因：多余列的读取、类型转换与 Python 对象构造都会产生开销，单行成本随列数线性增长；结果集越大，浪费的 I/O 与内存越显著。

优化建议：改为显式列名，只取调用方实际消费的字段。

位置：query 中的过滤条件

问题：语句中未体现结果行数上限；若 name 在 users 表上无索引，条件退化为全表扫描。

性能损耗原因：无 LIMIT 时结果规模不可控，耗时与内存随匹配行数线性增长；无索引时扫描成本为 O(n)，随表行数线性上升。

优化建议：补 LIMIT；确认 name 上存在索引，使查询从 O(n) 降为近似 O(log n)。

位置：resp = cursor.fetchall()

问题：一次性将全部结果行物化到内存后再返回。

性能损耗原因：内存占用为 O(n) 且峰值集中出现在返回前，无法边读边处理；大结果集下 GC 压力与内存峰值同步上升，遍历开始前需等待全部读取完成，首字节延迟被拉长。

优化建议：改为返回游标并按需迭代，或改用分页（LIMIT/OFFSET 或游标分页）控制单次物化规模。

位置：cursor.execute(query) 与字符串构造的 SQL

问题：SQL 以字符串拼接方式生成并直接执行，语句文本每次重新构造。

性能损耗原因：无法命中 SQLite 的预处理语句缓存，每次执行都要重新解析与生成执行计划；条件值以字面量嵌入还会使执行计划无法跨调用复用。

优化建议：改用参数化绑定，使语句文本稳定，从而复用已编译语句与执行计划。

位置：conn.close() 紧接 fetchall() 之后

问题：结果已全量物化后才关闭连接，连接持有时间覆盖了整个结果读取期。

性能损耗原因：连接占用窗口被不必要地拉长，在高并发下加剧连接资源的排队与争用；与流式读取方案相比，单位时间内可完成的查询数下降。

优化建议：在不改变返回形态的前提下，尽量缩短连接持有区间；若改为流式返回，则需重新设计生命周期归属。

位置：cursor = conn.cursor()

问题：每次调用都新建游标对象，且仅使用一次。

性能损耗原因：游标创建与销毁为固定小开销，单次可忽略，但在高频调用路径上累计可观。

优化建议：连接复用的前提下复用游标；单独存在时优先级低，可暂不处理。

【补充说明】
原始代码中的 query 文本不完整（止于 WHERE... '），以下评估基于其可见结构展开；若完整语句包含其他过滤条件或排序，索引与排序开销需按实际语句重新核算。

性能维度上，该实现的问题集中在三个可度量点：连接按调用新建（固定开销随调用次数线性放大）、SELECT * 与 fetchall() 组合（开销随列数与行数线性增长且内存峰值前置）、以及无上限的结果规模（耗时不可控）。这三者都属“单次调用可接受、规模化后显著劣化”的类型，评估结论取决于调用频率与表规模，而非代码行数。
