import sqlite3

def get_user(username):
    conn = sqlite3.connect('test.db')
    cursor = conn.cursor()
    query = "SELECT * FROM users WHERE... '"
    cursor.execute(query)
    resp = cursor.fetchall()
    conn.close()
    return resp



【架构评审结论】架构等级：有缺陷

【架构问题清单】

位置：get_user 函数整体（connect → cursor → SQL 构造 → execute → fetchall → close）

问题：连接建立、查询构造、语句执行、结果映射、资源回收五类职责全部内聚在同一个函数内，未形成任何端口 / 适配器或仓储边界。

架构层面影响：模块划分缺失，持久化细节与查询入口直接重叠；上层只能依赖该具体实现，无法替换存储，也无法在统一位置治理查询策略与事务语义。

重构建议：抽出 UserReader 端口与 SQLiteUserReader 适配器，get_user 退化为端口上的一个方法，业务层仅依赖抽象。

位置：conn = sqlite3.connect('test.db')

问题：具体驱动与连接字符串硬编码在业务函数体内。

架构层面影响：违反依赖倒置，高层模块反向依赖底层基础设施细节；环境切换、测试替身、多数据源扩展都必须修改业务代码，而非替换适配器。

重构建议：连接由组合根（配置层 / 工厂 / 构造注入）提供，仓储只消费抽象连接，模块顶部不直接暴露驱动依赖。

位置：conn 与 conn.close() 的生命周期

问题：资源生命周期由查询函数自行开启并自行终结，与查询职责绑定；且 close() 只覆盖顺序执行的正常路径。

架构层面影响：职责不单一；函数无法参与上层事务边界（请求级事务、跨查询原子操作），多个查询不能共享同一连接；资源归属悬浮在业务层，上层对事务可见性为零。

重构建议：将连接与事务交由作用域（请求作用域 / Unit of Work）持有，查询函数只消费传入连接；终结动作交给统一的作用域出口，而非散落在业务函数内。

位置：return resp（cursor.fetchall() 的裸元组）

问题：向外暴露基础设施层的行结构，缺少领域模型或 DTO 边界。

架构层面影响：契约不稳定，调用方按位置索引取值，表结构演进会直接渗透到上层；缺少领域对象，跨模块复用成本上升。

重构建议：在适配器边界完成行到对象的映射，返回 User 领域对象或 UserDTO 列表，调用方只依赖具名契约。

位置：函数签名 def get_user(username)

问题：命名表达“取单个用户”，实现返回列表，接口契约与语义不一致。

架构层面影响：模块对外语义模糊，调用方对返回值基数的预期会错位；后续在“单条 / 列表”之间演进将构成破坏性变更。

重构建议：明确基数——改为 find_users_by_name() 返回列表，或返回 Optional[User] 并以唯一约束为前提。

位置：query = "SELECT * FROM users WHERE ..." 与 cursor.execute(query)

问题：查询语句以字符串形式内联在业务流程中，没有独立的查询构造边界。

架构层面影响：查询定义散落于业务函数，无法集中管理、复用或替换为查询构建器 / ORM；同一实体的查询易在不同模块被复制。

重构建议：将语句定义收敛进仓储或独立的查询对象，业务层只表达查询意图。

位置：execute / fetchall 的异常传播路径

问题：无异常分层，驱动异常未经转译直接穿透到调用方。

架构层面影响：上层被迫编译依赖 sqlite3 的异常类型，基础设施细节外泄至领域边界；替换存储时上层捕获逻辑全部失效。

重构建议：在适配器内捕获驱动异常并转换为领域异常（如 RepositoryUnavailable / EntityNotFound），保持端口层异常契约稳定。

位置：模块级 import sqlite3

问题：直接绑定具体驱动，缺少存储抽象层。

架构层面影响：可扩展性受限——迁移至其他数据库、引入 ORM 或读写分离时需跨模块修改依赖点，而不是新增一个适配器。

重构建议：端口层仅依赖存储协议，驱动引入下沉到适配器模块。

【补充说明】
相比于上一版本，conn.close() 的补入修正了“完全不留收尾动作”的问题，但这只是把资源处理从“缺失”提升为“由业务函数自行管理”，职责归属并未回到正确的架构位置：正常路径关闭并不改变“连接生命周期不应由查询函数决定”这一事实。资源收尾的完整性属于实现细节，本质的架构问题仍是生命周期归属与分层边界缺失。

从架构维度看，该实现处于零分层状态：单一函数承担编排、连接管理、查询构造与结果映射四种角色，并对具体基础设施形成双向硬依赖，依赖倒置与职责单一均未落地。

需要明确取舍：代码体量小、调用方唯一时，若确认是一次性脚本或原型，引入端口 + 适配器 + 领域对象属于收益有限的重构；一旦其进入服务端、被多处复用或需要可测试性、可替换存储，上述分层就从“过度设计”转为必要成本。架构成熟度应随调用方数量与变更频率增长，而不是按函数长度判断。
