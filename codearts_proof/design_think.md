# design_think · 为什么拆分多 Skill，而不是单 Prompt 完成全部评审

> 本文档回答一个评委必然会问的问题：把四维评审塞进一个大 Prompt 也能出结果，为什么要费力拆成 5 个 Skill？

---

## 一、出发点：教学需要的是"分歧"，不是"答案"

普通 AI 代码评审工具的目标是给出"最优修复方案"。但真实工业开发中，安全、性能、架构、编码规范的目标经常互相矛盾：

- 为了安全加输入校验和权限检查，性能会受损；
- 为了性能做连接复用和缓存，异常状态隔离与安全边界会变复杂；
- 为了架构清晰抽 DAO 层、引入依赖注入，代码量和间接性上升，对小脚本属于过度设计。

软件工程课堂最缺的素材恰恰是这种**没有唯一正确答案的取舍案例**。如果评审 AI 天然倾向"调和矛盾、给出唯一答案"，它就制造不出教学所需的分歧素材。

## 二、方案对比

### 方案 A：单个大 Prompt，一个模型同时完成四维评审

缺陷：

1. **自我调和**：大模型倾向输出自洽统一的结论，即使现实存在冲突也会把分歧抹平，达不到教学目的；
2. **角色混淆**：一个上下文里同时扮演四个专家，评估维度互相渗透，"安全评审"里混进规范意见；
3. **无法独立迭代**：改安全逻辑要动整个 Prompt，牵一发动全身；
4. **不可扩展**：想新增"兼容性""可测试性"维度只能继续膨胀单 Prompt。

### 方案 B（本项目选择）：4 个完全隔离的独立 Skill + 1 个汇总 Skill

优势：

1. **保留真实分歧**：各 Skill 上下文隔离、只关心本维度、互不干涉，输出不受其他视角污染，分歧是真实涌现的而非编排出来的；
2. **可独立迭代**：每个 Skill 的 Prompt 单独调试、单独回归（本项目每个 Skill 均有 v1 → final 迭代记录可查）；
3. **可扩展**：新增维度 = 新增一个 Skill + 流水线加一条并行分支，存量不动；
4. **符合智能体单一职责设计思想**：评审与消解分离——"制造观点"和"评判观点"由不同角色承担，汇总 Skill 被明确约束为"不单方面判定对错，只呈现权衡代价"。

## 三、关键设计决策

| 决策 | 选择 | 理由 |
| ---- | ---- | ---- |
| 评审 Skill 数量 | 4 个（安全/性能/架构/规范） | 覆盖软件工程评审的四大经典视角，且它们之间天然存在目标张力，足够产生高质量冲突；再堆数量只增加噪音 |
| 汇总 Skill 立场 | 中立、不给唯一答案 | 教学导向：把权衡判断留给师生讨论，这是产品定位而非技术妥协 |
| 输出格式 | 每个 Skill 强制结构化 | 使汇总 Skill 可按区块对齐比对，冲突识别可复现 |
| 执行方式 | 流水线并行 | 一次输入同时得到四份报告，延迟约等于最慢一个 Skill 而非四者之和 |

## 四、当前局限

1. Web 交互界面为原型演示，暂未对接码道开放 API，无法直接在网页提交代码触发流水线；
2. 测试用例目前以 Python 为主，尚未扩展 Java、C++ 等；
3. 冲突识别依赖大模型，极少数场景可能漏识别细微的权衡冲突；
4. 冲突质量依赖测试代码的设计——平淡的代码四方意见一致，是正常现象（用例 1 即用于验证这一点）。

## 五、后续迭代方向

1. 对接码道开放 API，打通前端与流水线；
2. 扩充多语言支持与教学案例库（按"安全-性能冲突""架构-规范冲突"等类型组织）；
3. 优化汇总 Skill 的冲突识别 Prompt，提升细微分歧的发现率；
4. 探索课堂反馈闭环：学生对方案的选择数据反哺案例库分级。
